# Markus v1.1 — Planning

v1 closed its board 10 of 10 and the test suite is green, but the app that
came out of it cannot be judged as a Markdown editor. v1.1 is the release
that makes Markus **evaluable on macOS**: a document window that behaves
like a Mac app, a Preview that renders Markdown instead of colouring its
syntax, chrome that does what its labels claim, and a text view that does
not redraw the whole document quadratically.

This is a **correction and completion** release, not a feature release.
Almost everything here was already promised by v1 and either shipped
broken, shipped as a stub, or was dropped between Requirements and
tickets. Where v1.1 adds something genuinely new, it says so.

## Background

Markus is a free, open-source, native Markdown app for macOS, iOS, and
iPadOS. It opens ordinary files on disk. No account, no vault, no
telemetry, no subscription. MIT licensed.

v1 (see `docs/ai/Markus/v1/`) chose architecture **C**: SwiftUI chrome,
a custom TextKit 2 view that owns `NSTextLayoutManager`, cmark-gfm as
the parser, and a Swift block index. That spine is sound and v1.1 keeps
it. The folding mechanism in particular is correct and was hard-won —
folds hide via zero-height `FoldingTextLayoutFragment`s, the buffer is
never rewritten, and disk always receives the full unfolded UTF-8 source.
cmark-gfm is real and correctly configured with GFM extensions.

What v1 did not deliver is everything wrapped around that spine. Three
gaps matter most:

1. **You cannot type.** `FoldingTextView` has no `keyDown`, no
   `insertText:`, no `NSTextInputClient`, no caret, and no selection
   drawing. The only text mutation paths in the shipped app are
   Find/Replace and `insertTextAtCaret`, which ignores the caret and
   always inserts at offset 0. `DocumentSession.autosave()` is called
   only from a unit test. `MarkdownDocument` sets `hasUndoManager = false`.
2. **Preview is colourised source, not rendered Markdown.** The renderer
   only adds attributes to the untouched buffer, so a reader sees `##`,
   pipe-and-dash table rules, `- [ ]`, `[text](url)` and fence backticks.
   The parser emits no spans at all for emphasis, strong, block quotes,
   lists, images, or thematic breaks, so `**bold**` renders as the literal
   characters. Heading level is ignored — every heading is 22pt.
3. **Fold all / unfold all does not exist.** It is named in the v1
   planning file, in Requirements R4, and in both acceptance-criteria
   lists, but it never made it into a ticket and no such code exists.
   The v1 completion note claims it shipped.

On top of that, the macOS document window is unusable as a Mac app: no
File menu, no Edit menu, a title bar loaded with buttons that belong in
menus, several of which do nothing.

v1.1 targets **macOS only**. The shared editor, parser, and block index
are cross-platform, so changes there must keep the iOS and iPadOS
destinations building and green — but no new iPhone or iPad UI is in
scope. Their turn comes after macOS is worth evaluating.

## Goals

- Make the macOS window feel like a Mac app: correct launch geometry, a
  real File and Edit menu, and a title bar that holds only what belongs
  in a title bar.
- Make Preview **render** GFM instead of tinting its syntax, so the
  reading experience the product is built around actually exists.
- Finish the folding feature v1 promised: fold all, unfold all, a fence
  placeholder, folds that survive edits, and folds that persist per file.
- Replace the settings side-panel with a proper full-viewport settings
  surface reachable from a left ribbon rail, and give the theme picker
  the hover-to-proxy behaviour that was specified.
- Fix or remove every piece of chrome that currently misleads: the dead
  Open button, the empty folder tree, the inert minimap, the zoom
  buttons.
- Get drawing and styling off their quadratic and full-reparse paths so a
  real-world document is smooth.
- Decide and act on the editing gap (see **The editing decision** below).

## Non-goals

v1.1 will not include:

- New iPhone or iPad UI work (shared-layer changes must not regress
  those builds, but their chrome waits)
- Anything on the v1 Skip list: side-by-side Source and Preview, PKM,
  AI, plugins, user key remapping, math, Mermaid, first-class raw HTML
  preview, Windows or Linux, multi-cursor, project-wide search, PDF/RTF
  export
- Language-aware syntax highlighting inside fenced code
- A rope or mmap buffer (still a later spike, still not a hidden
  requirement)
- Folding lists, block quotes, or `#region`
- Distraction-free or typewriter modes
- Redesigning the theme palettes themselves — the six named themes stay;
  only the picker's behaviour changes

## Target users

Unchanged from v1: people who keep Markdown as files and want a fast
native app. But v1.1 has one user in front of all of them — **the
maintainer trying to evaluate whether v1 was worth building on.** Every
item here is chosen because it currently blocks that judgement.

## User stories

- As a Mac user, I launch Markus and get a window sized and placed like
  every other Mac app, not a small window parked at the edge of my
  screen.
- As a Mac user, I press ⌘N, ⌘O, or ⌘S and the File menu does what the
  whole platform taught me it does.
- As a Mac user, I reopen a recent file from **File ▸ Open Recent**,
  where recents live on every other Mac app.
- As a reader, I open a document in Preview and see rendered
  Markdown — bold that is bold, headings that scale by level, lists and
  quotes that read as lists and quotes, tables laid out as tables — not
  the source with colours on it.
- As a reader on a long document, I choose **Fold All** to collapse every
  section at once, then **Unfold All** to bring it back.
- As a reader, I fold a fenced code block and see a placeholder telling
  me what I collapsed, instead of the block silently vanishing.
- As a user with a notes folder, I open that folder and actually see my
  Markdown files listed.
- As a user, I open the settings from a gear at the bottom of a ribbon
  rail, get a full-viewport settings surface with a category list on the
  left and the chosen setting on the right, and close it with a close box.
- As a user choosing a theme, I hover a theme card and a proxy document
  below the cards previews it; I click and it applies.
- As a user, I open the library of Markdown files in the current folder
  from a hamburger at the top of the same ribbon rail.
- As a user, the zoom controls change the text size, and the minimap
  shows me where I am in the document and takes me where I click.
- As a writer, I switch to Source, put the caret where I want it, type,
  undo, and save — and the file on disk is the full unfolded Markdown.
- As a reader, I stay in Preview and it stays out of my way: I can select
  and copy what I read, and I cannot accidentally type into it.

## The editing decision — settled

**Real text input is in v1.1**, and it is scheduled **last**, after
chrome, Preview, folding, and performance have landed. That ordering
means editing gets built on a text view that has already been fixed, and
it keeps the release useful at every intermediate point.

Editing is the largest single item here. On a view that owns its own
layout manager it means caret geometry and blinking, selection drawing,
mouse-drag and double/triple-click selection, `NSTextInputClient`
conformance for IME and dictation, undo/redo coalescing, accessibility,
and rewiring the dirty and `updateChangeCount` path that v1 already
flagged as unreliable.

**Editing happens in Source mode only. Preview is a reading surface and
is read-only.** This follows v1's own product intent — "read the file,
fold what you do not need, and edit only when something is wrong",
"switch to Source, edit GFM, and save" — and it is what makes both this
release's headline items affordable at once. Source is monospace and 1:1
with the buffer, so caret and selection geometry map directly to source
offsets with no translation layer. A rendered Preview, by contrast,
displays substituted text whose offsets do not match the buffer;
supporting a caret there would mean a full WYSIWYG mapping problem that
this release is not taking on. Keeping Preview read-only removes that
problem entirely rather than deferring it.

## What v1.1 addresses

### A. macOS window and menus

1. **Launch geometry.** The window is created at a fixed 960×720 at
   origin with no positioning. It should open pinned to the top-left of
   the active screen's visible frame at three-quarters of that frame's
   width and height.
2. **File menu.** Add **New**, **Open…**, **Open Folder…**, **Open
   Recent** (submenu), and **Save**, with standard shortcuts. Remove the
   corresponding Open, Open Folder, Save, and Recents controls from the
   document title bar.
3. **Edit menu.** Add **Fold All** and **Unfold All** (Fold All replaces
   the title-bar "Fold" button, which today folds a single block, not
   all), plus **Find** and **Go to Line**. Remove those buttons from the
   title bar.
4. **Title-bar cleanup.** Remove **Toggle** — it duplicates the
   Source/Preview segmented control that R3 requires and that already
   sits in the title bar. Remove **Tree**, which merely re-triggers Open
   Folder. What remains in the title bar is the Source/Preview control.
5. **Dead Open button.** The Open button presents nothing. Open Folder
   works. Both are `.fileImporter` modifiers chained onto the same view,
   which SwiftUI does not support — one silently wins. Whatever replaces
   them must not repeat this.

### B. Left ribbon rail, library, and settings

6. **Ribbon rail.** A slim vertical rail pinned to the left of the
   document, holding a hamburger icon at the top and a gear icon at the
   bottom.
7. **Library panel.** The library panel *is* the tree view, given a
   proper home and a proper affordance. It shows a filtered hierarchy of
   the files Markus can open — Markdown only, nested folders included,
   dotfiles and other file types excluded. The hamburger at the top of
   the ribbon rail toggles it open and closed.

   With a single file open, the library starts **closed**. It opens only
   when the user presses the hamburger or uses Open Folder. Note that it
   cannot fall back to showing the open file's *containing* folder:
   opening one file grants a security scope for that file alone, so
   enumerating its parent is denied under the sandbox. Pressing the
   hamburger with no folder in the session should therefore present an
   empty state offering **Open Folder…**, not silently do nothing.
8. **Settings surface.** The gear opens settings that fill the viewport:
   a category list in a left panel, the active setting (themes first) in
   a right panel, and a close box. This replaces today's side panel,
   which cannot be dismissed because its Done button is hoisted out of a
   nested `NavigationStack` into the window toolbar.

### C. Theme picker

9. **Proxy document.** Below the six preset cards and the custom card,
   show a single proxy document. Hovering a card previews that theme in
   the proxy; clicking applies it. Today each card renders its own
   miniature editor and hover repaints the real document, which is both
   heavy and jarring.
10. **Selection must work.** Theme cards currently cannot be selected.
    Root cause is not yet isolated; a suspect is the `FoldingTextView`
    embedded inside each card's `Button`. Moving to a single proxy may
    dissolve this, but selection must be proven working, not assumed.

### D. Folder tree

11. **Files must appear.** Selecting a folder yields an empty panel.
    `MarkdownFolderTree.children(of:)` enumerates with the **path-based**
    `contentsOfDirectory(atPath:)`, which is denied under the App Sandbox
    that `Markus.entitlements` enables; enumeration has to go through the
    security-scoped URL.

### E. Preview rendering

12. **Render, don't tint.** Preview must present Markdown as a document:
    headings scaled by level, bold and italic applied, lists and block
    quotes shaped, tables laid out, links presented as links, and
    Markdown punctuation not shown as literal text.
13. **Cover the dialect.** The parser walk emits no spans for emphasis,
    strong, block quotes, lists, images, or thematic breaks. GFM
    coverage has to be complete or the truthful-preview claim in v1's R1
    stays false.
14. **Fixtures that would have caught this.** The v1 GFM fixture contains
    no bold, italic, block quote, nested list, image, or heading below
    H1, and its test only asserts that an attribute was attached to a
    source range. Fixtures and assertions must exercise what a reader
    actually sees.

### F. Folding completion

15. **Fold All / Unfold All**, per A.3 — the feature R4 required and no
    code implements.
16. **Fence placeholder.** v1 specified a fenced block folds to "the
    opening fence and a short placeholder". Today the body simply
    disappears with no marker.
17. **Fold persistence.** v1 specified folds persist per file in app
    state. `FoldStore` is an in-memory `Set` and nothing is written.
18. **Fold repair across edits.** A `FoldID` is `kind + startLine`, and
    rebuilding the block index after an edit leaves folds pointing at
    stale line numbers. v1's Requirements called for repair on rebuild;
    there is none. This becomes urgent the moment typing exists.

### G. Minimap and zoom

19. **Minimap.** Improve it for macOS in this release. Today it draws
    uniform grey bars, one per source line, with no token colour, no
    viewport indicator, and no click-to-scroll — the
    `sourceLine(atViewY:)` API exists but nothing calls it — and it
    refreshes only when SwiftUI happens to re-render. It should reflect
    document structure, indicate the current viewport, scroll on click,
    stay fold-aware, and refresh when the document does. At the 5 MB
    target it also has to downsample rather than draw a bar per line.
20. **Zoom controls.** The `−` and `+` buttons in the status bar are
    reported as doing nothing. They do call `setZoomScale`, so the fault
    is downstream — likely the view frame or redraw not following the
    change. Needs isolating, not guessing.

### H. Performance

21. **Quadratic drawing.** Every `draw()` enumerates *all* layout
    fragments with `.ensuresLayout` and no dirty-rect culling, and
    `drawGutter` calls `packedSourceLineEntries()`, which is
    O(lines × fragments). Each redraw is at least quadratic in document
    size.
22. **Full reparse on every styling pass.** `applyStyling` runs a
    complete cmark parse on every fold toggle, theme change, zoom step,
    and text-container resize. Folding a heading in a large file reparses
    the whole document.
23. **Repeated `SourceMap` construction.** `BlockIndex.build` allocates a
    fresh `SourceMap` inside the loop for every fenced code block.
24. **A stated budget: 5 MB, 200 ms.** v1 assumed "reasonable document
    sizes" without ever naming one. v1.1 targets **saved Markdown
    documents up to 5 MB**, with **200 ms as the base ceiling for
    discrete operations** — open, fold, unfold, fold all, unfold all,
    mode switch, theme change, go-to-line. Revisit the figure once
    there is something to measure.

    **200 ms does not apply to continuous interactions.** Scrolling and
    keystroke-to-glyph are judged per frame, not per operation: at 60 Hz
    the budget is ~16 ms, and a 200 ms scroll frame is roughly twelve
    dropped frames. An implementation that satisfied a flat 200 ms rule
    everywhere would still feel broken. Requirements should state two
    budgets — a 200 ms discrete-operation ceiling and a frame budget for
    scroll and typing — rather than one number covering both.

    The suite also needs a large-document fixture at the 5 MB target.
    None exists today.

### I. Test integrity

25. **Remove tautologies.** `MacOnlyChromeTests` asserts that
    `#if os(macOS) true #else false` evaluates to `true` on macOS. It
    cannot fail and proves nothing. Several other chrome tests assert
    compile-time flags rather than live view behaviour.
26. **Test what the user sees.** Menu commands, fold-all, theme
    selection, tree population, and Preview rendering all need tests that
    would fail if the feature were removed.

### J. Cross-window consistency

27. **Theme is global.** Selecting a theme applies it to every open
    window and tab, immediately. Today each `MarkdownDocument` builds its
    own `DocumentHost` and therefore its own `ThemeStore`, so two Mac
    tabs can disagree. The store has to become shared, and a change has
    to broadcast to every open document rather than only the one that
    made it.

## Recommended direction (to ratify in Requirements)

Three of the open questions were delegated for a recommendation. These
are proposals, not decisions — `bora-design` ratifies them before
Requirements are written. They are recorded here because they hang
together as one answer.

### Rendered Preview: paragraph substitution, one buffer

**Recommendation: keep a single authoritative `NSTextStorage` holding the
raw Markdown, and render Preview through
`NSTextContentStorageDelegate` paragraph substitution.**

The delegate hook lets the content storage hand the layout manager a
*different* attributed string for a given source paragraph while the
backing store keeps the original bytes. In Preview the delegate returns a
rendered paragraph — heading sized by level, emphasis applied, markup
punctuation simply absent from the substituted string. In Source it
returns nothing and the raw bytes lay out as they do today.

Why this over the alternatives:

- **It is the only option that can actually hide markup.** Attribute-only
  styling — what v1 does — cannot remove `##`, `**`, or backticks from
  the display. Faking it with clear foreground colours or near-zero font
  sizes is the same class of hack as the collapsed paragraph styles that
  v1's review already rejected under N3.
- **It preserves disk truth for free.** The buffer is never rewritten, so
  R5 and N3 hold by construction rather than by discipline.
- **It preserves the fold mechanism.** Folds collapse layout *elements*;
  substitution replaces an element's contents. The two compose cleanly
  and the existing `FoldingTextLayoutFragment` work survives intact.
- **It preserves the source mapping.** Every substituted paragraph still
  carries its source element range, so source line numbers, go-to-line,
  outline jump, and the minimap keep a real anchor.
- **It fixes the performance problem as a side effect.** Substitution is
  lazy and per-paragraph — the layout manager asks only for what it is
  about to lay out. That removes the full-document restyle that currently
  runs on every fold toggle, theme change, and zoom step (H.22).

What we need to establish before committing, in rough risk order:

1. **Tables are a true grid** (decided). A GFM table is one cmark node
   spanning several source lines, but substitution is per-paragraph, so
   a grid needs an `NSTextAttachment` whose cell is custom-drawn and
   sized from measured column widths. This is the single largest unknown
   in the approach. It deserves its own ticket, sequenced early enough
   that failing it can still reopen design rather than stranding the
   release. It also collapses several source lines into one attachment
   line — which the block-anchored gutter already accommodates, and
   which is a further argument for it.
2. **Selection and copy in Preview** (decided). Preview is read-only but
   selectable, and copying yields **source Markdown**, not the rendered
   substitution. Selection therefore has to map rendered offsets back to
   source ranges — modest for substituted paragraphs, but a table
   attachment is one opaque glyph, so selecting a table must resolve to
   its whole source range.
3. **Incremental rebuild.** How much of the block index and substitution
   cache must be invalidated per edit. Bounded by the decision that
   typing fluency is *not* required at 5 MB (see Constraints), but still
   the main determinant of whether editing feels good at ordinary sizes.
4. **Images are deferred** (decided). Real inline attachments are the
   eventual target, not a placeholder — but they land in the backlog,
   not v1.1. The attachment infrastructure built for tables should not
   preclude them.

### Preview gutter: block-anchored numbers

**Recommendation: Source shows a number for every source line. Preview
shows fold chevrons for every foldable block plus a source line number at
each rendered block's start, not one per visual line.**

Once a rendered paragraph no longer occupies the same number of visual
lines as its source, per-line numbering in Preview is a fiction. Block
anchoring stays honest, keeps the numbers useful for the things that
consume them — folding, go-to-line, outline, the minimap — and matches
what v1 already accepted when it noted that wrapped Preview blocks look
sparse in the gutter.

**This revises R6.** v1 required source line numbers in both modes;
Requirements should restate it as *per-line in Source, block-anchored in
Preview*.

### Menus: AppKit main menu

**Recommendation: build an AppKit main menu in the app delegate and route
actions through the responder chain.**

The app is already `NSDocument`-based, which is precisely what makes
AppKit the easy path rather than the fallback. `NSDocumentController`
supplies New, Open, Save, and Save As through the responder chain with no
custom code, and it populates the **Open Recent** submenu automatically —
which is item A.2 done for free, and better than the hand-rolled recents
menu v1 shipped. Custom items (Fold All, Unfold All, Find, Go to Line)
become menu items whose action targets `nil` and are implemented on the
document or its content view controller.

SwiftUI `.commands` is the weaker choice here even though it can attach
to a `Settings`-only scene: its enablement and routing depend on SwiftUI
focus, and this app's windows are `NSWindow`s created by hand hosting a
`NSHostingController`, so focus-based routing to "the active document" is
exactly where it is least reliable. AppKit also cannot break `NSDocument`
tabbing, which the v1 completion note explicitly warns about.

## Constraints

- **Architecture C stands.** SwiftUI chrome, Markus-owned TextKit 2
  layout, cmark-gfm, Swift block index. v1.1 fixes and completes this
  stack; it does not replace it. If something here proves impossible on
  that stack, stop and reopen design rather than inventing a fourth one.
- **Folding stays a layout concern.** Zero-height owned fragments. Never
  rewrite the buffer, never squash paragraph styles. v1 already made this
  mistake once and corrected it.
- **Files remain the source of truth.** Folds, theme, recents, window
  state, and zoom live in app storage. Saving writes the complete
  unfolded UTF-8 source and nothing else.
- **One mode at a time**, default Preview. No split view.
- **Preview is read-only; editing is Source-only.** See *The editing
  decision — settled*.
- **Theme is global**, not per-window.
- **5 MB is the ceiling for *reading* an already-saved document.**
  Opening, scrolling, folding, and unfolding must stay comfortable at
  that size. **Typing fluency at 5 MB is explicitly out of scope** —
  authoring documents that large is a later problem. A 5 MB document
  must still be editable without hanging or corrupting, just not
  guaranteed fluid.
- **GFM is the dialect.** CommonMark plus tables, task lists,
  strikethrough, footnotes. No house format.
- **macOS is the target; iOS and iPadOS must not regress.** Any change to
  the shared editor, parser, or block index still verifies on all three
  destinations. macOS-only chrome verifies on macOS.
- **Menus are platform-standard.** Use the conventional macOS placements
  and shortcuts rather than inventing a layout.
- **No account, no telemetry, no network requirement** for core editing.

## Success criteria

v1.1 is working when all of the following are true on macOS:

- Markus launches into a window pinned to the top-left of the active
  screen's visible frame at three-quarters of its width and height.
- File contains New, Open…, Open Folder…, Open Recent, and Save, all
  functional with standard shortcuts. Edit contains Fold All, Unfold All,
  Find, and Go to Line. The document title bar contains the
  Source/Preview control and no Open, Open Folder, Save, Recents, Fold,
  Toggle, Find, Go to Line, or Tree buttons.
- Opening a folder lists its Markdown files, including nested folders,
  excluding dotfiles and non-Markdown files, under the App Sandbox.
- A left ribbon rail shows a hamburger at the top that toggles the
  library panel and a gear at the bottom that opens a full-viewport
  settings surface with a category list, a detail panel, and a working
  close box. With only a single file open the library starts closed, and
  opening it with no folder in the session offers Open Folder… rather
  than showing nothing.
- The theme picker shows six presets plus custom above a single proxy
  document; hovering a card previews in the proxy, clicking applies, and
  the applied theme persists across relaunch.
- Preview of a GFM fixture reads as a rendered document: headings scale
  by level, bold and italic are applied, lists and block quotes are
  shaped, tables render as a true grid with aligned columns, and Markdown
  punctuation is not displayed as literal text. Emphasis, strong, block
  quotes, lists, tables, and thematic breaks are all covered. Images are
  not rendered in v1.1 — inline attachments are backlog — and must
  degrade to readable styled text rather than raw syntax.
- Fold All collapses every foldable block and Unfold All restores them; a
  folded fence shows its opening fence plus a placeholder; folds persist
  per file across relaunch and survive an edit elsewhere in the document.
- Source shows a line number for every source line; Preview shows fold
  chevrons and a source line number at each rendered block's start.
  Go-to-line, outline jump, and the minimap agree with both.
- The minimap reflects document structure, indicates the current
  viewport, scrolls on click, and stays fold-aware.
- The zoom controls visibly change text size in both modes.
- Selecting a theme applies it immediately to every open window and tab,
  and the choice survives relaunch.
- On a saved 5 MB Markdown document, discrete operations — open, fold,
  unfold, fold all, unfold all, mode switch, theme change, go-to-line —
  complete within 200 ms, and scrolling holds its frame budget. Drawing
  is not quadratic in document size, and folding, theme changes, and zoom
  steps do not trigger a full reparse or a full-document restyle.
- **Editing:** in Source, the caret is visible and placeable, typing
  inserts at the caret, selection works by mouse and keyboard, undo and
  redo work, the dirty flag and `updateChangeCount` follow every change
  including undo, and saving writes the complete unfolded buffer.
  Preview is read-only but selectable, and copying from it yields source
  Markdown — including when the selection covers a table.
- The test suite contains no assertion that cannot fail, and the features
  above are covered by tests that would fail if the feature regressed —
  including a large-document fixture at the 5 MB target.
- The full suite passes on macOS, iPhone simulator, and iPad simulator.

## v1.1 feature set

### Must

Roughly in delivery order. Editing is last by design.

1. macOS window geometry (A.1)
2. File and Edit menus via AppKit; title-bar cleanup; dead Open button
   (A.2–A.5)
3. Folder tree populates under sandbox (D.11)
4. Fold All / Unfold All (F.15)
5. Left ribbon rail, library panel, full-viewport settings (B.6–B.8)
6. Theme proxy document; theme selection works; theme is global
   (C.9–C.10, J.27)
7. Preview renders GFM via paragraph substitution, with complete span
   coverage and fixtures that exercise what a reader sees (E.12–E.14),
   including **tables as a true grid** — the release's biggest technical
   unknown, so sequence it early enough that failure can reopen design
8. Performance to the 5 MB budget: viewport drawing, lazy styling, no
   reparse per interaction (H.21–H.24)
9. Minimap improvements for macOS (G.19)
10. Text input in Source: caret, selection, undo/redo, dirty and
    `updateChangeCount` wiring — plus fold repair across edits (F.18),
    which only becomes reachable once typing exists

### Should

- Fence fold placeholder (F.16)
- Fold persistence per file (F.17)
- Zoom controls fixed (G.20)
- Test-integrity pass (I.25–I.26)

### Later

- **Inline image attachments in Preview** — real rendered images with
  sizing and sandboxed loading, not placeholders. Decided as the eventual
  target; deferred out of v1.1.
- **Authoring at 5 MB** — fluid typing in very large documents, which
  needs incremental reparse rather than debouncing
- iPhone and iPad chrome brought up to the macOS standard
- iOS/iPad line-number toggle in settings (R7's UI half, still missing)
- Status bar and fold-current following the live caret rather than the
  last jump
- Shared theme across Mac tabs, or an explicit per-window choice
- Security-scope honesty: persist the OS `startAccessing` result, stop
  storing path-only recents when bookmarking fails, fail moved-folder
  recents cleanly
- Setext headings in the outline
- Large-document spike (rope / mmap) if `NSTextStorage` falls over
- Project-wide search, multi-cursor, PDF/RTF export

### Skip

Unchanged from v1: side-by-side Source and Preview, PKM, AI, plugins,
user key remapping, math, Mermaid, raw HTML as first-class preview,

## Decisions taken

Settled 2026-08-16. These are product decisions; the architecture
proposals in *Recommended direction* still need ratifying in
`bora-design`.

- **Editing is in v1.1**, scheduled last. **Preview is read-only;
  editing is Source-only.**
- **Preview gutter is block-anchored** — per-line numbers in Source,
  block-start numbers plus chevrons in Preview. Revises R6.
- **One authoritative `NSTextStorage`**, with Preview rendered through
  `NSTextContentStorageDelegate` paragraph substitution.
- **Minimap is improved for macOS** in this release, not dropped.
- **The library panel is the tree view**, toggled by the ribbon
  hamburger, showing a filtered hierarchy of openable Markdown files.
- **5 MB is the document ceiling** for comfortable open, scroll, fold,
  and unfold.
- **Menus are an AppKit main menu** routed through the responder chain.
- **Theme is global** across all windows and tabs.
- **Tables render as a true grid** via a custom-drawn `NSTextAttachment`.
  Highest-risk item in the release.
- **Images are deferred to the backlog.** Real inline attachments are the
  eventual target, not placeholders; v1.1 degrades them to styled text.
- **5 MB applies to reading saved documents.** Typing fluency at that
  size is out of scope; authoring large documents is a later problem.
- **200 ms is the discrete-operation ceiling**, to revisit once there is
  something to measure. Scroll and typing are judged per frame instead.
- **The library starts closed with a single file open**, and opens only
  via the hamburger or Open Folder.
- **Preview is selectable and copies source Markdown.**

## Open questions

- **What document size must typing be fluid at?** 5 MB is settled as the
  *reading* ceiling and explicitly not the typing target — but the typing
  target has no number yet. Requirements need one, or the editing tickets
  have no performance bar. A plausible starting point is fluency up to
  roughly 1 MB, degrading gracefully above that.
- **The frame budget for scroll and typing.** Implied by the 200 ms
  decision excluding continuous interaction, but not yet stated. 60 Hz
  (~16 ms) is the obvious default.
- **Where does the table-grid spike sit in the order?** It is the
  release's biggest unknown and the one item that could reopen design, so
  it may deserve to run ahead of the chrome work rather than inside the
  Preview ticket.
