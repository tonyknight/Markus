## Description

Today's minimap draws uniform grey bars, one per source line, with no
token colour, no viewport indicator, and no click-to-scroll — the
`sourceLine(atViewY:)` API exists but nothing calls it — and it
refreshes only when SwiftUI happens to re-render. This ticket improves
it for macOS: structural rendering, a viewport indicator, click-to-scroll,
fold-awareness, and downsampling at the 5 MB target.

## Acceptance criteria

- [ ] The minimap reflects document structure rather than uniform bars
      (R18).
- [ ] It indicates the current viewport (R18).
- [ ] Clicking scrolls to the corresponding location, using the existing
      `sourceLine(atViewY:)` API (R18).
- [ ] It stays fold-aware (folded regions do not show as if expanded)
      (R18).
- [ ] At the 5 MB target it downsamples rather than drawing one bar per
      line (G.19).
- [ ] It refreshes when the document changes, not only when SwiftUI
      happens to re-render (G.19).

## Context

### T01: Structural rendering (not uniform grey bars)

Today `MacMinimapView.draw()` fills one identical grey rect per
`SourceLineMap.Entry` — no distinction between a heading, a fenced-code
line, or a body line. Give `MinimapSnapshot` two new sets built from
`editor.blocks` in `MacMinimapChrome.snapshot(from:)` — `headingLines:
Set<Int>` and `fenceLines: Set<Int>` (populated by switching on each
`Block.kind`, unioning `block.lines`) — plus a `kind(forSourceLine:) ->
MinimapBarKind` helper (`.heading` / `.fence` / `.body`, heading checked
before fence). Add a new pure, testable `MinimapRenderer.bars(from
snapshot:) -> [MinimapBar]` (one `MinimapBar { y, height, kind, coverage
}` per visible `SourceLineMap.Entry` at this stage — downsampling is
T04) where `coverage` is `entry.height` normalized against the tallest
entry in the snapshot (reuses layout data already computed for
`SourceLineMap`, no extra text scanning). `MacMinimapView.draw()` fills
each bar with a colour keyed by `kind` (heading gets
`NSColor.controlAccentColor`, fence a distinct secondary tint, body the
existing `secondaryLabelColor`) and a width scaled by `coverage`,
replacing the uniform-width/uniform-colour loop over raw entries. Tests:
(1) on the existing heading/paragraph/fence fixture, assert
`snapshot.kind(forSourceLine:)` returns `.heading` for the heading line,
`.fence` for the fence's opening line, and `.body` for the paragraph
line; (2) `MinimapRenderer.bars(from:)` produces bars whose `kind` set
contains all three cases for that fixture (proves the render plan is not
uniform); (3) a rasterization test — render `MacMinimapView.draw()` into
an `NSBitmapImageRep` via `NSGraphicsContext(bitmapImageRep:)` (mirroring
`TableAttachmentTests.imageForBoundsRendersAGridNeitherBlankNorSolid`'s
approach, adapted to a plain `NSView.draw`) and sample pixel colour at
the heading bar's, fence bar's, and a body bar's computed y — assert
they are not all equal, i.e. real drawn pixels differ, not just
in-memory data (N9).

### T02: Viewport indicator overlay

Expose the editor's current visible region: add
`FoldingTextView.currentVisiblePackedRect() -> CGRect` (thin public
wrapper around the existing private `visiblePackedRect()`, same shape as
the existing `viewportContainsPackedY` wrapper). Add
`visiblePackedRect: CGRect` to `MinimapSnapshot`, populated in
`snapshot(from:)`. Add a pure `MacMinimapChrome.viewportRect(in
minimapBounds: CGRect, snapshot: MinimapSnapshot) -> CGRect`: scales
`snapshot.visiblePackedRect` by `minimapBounds.height /
snapshot.packedHeight`, same scale factor `draw()` already uses for
bars. `MacMinimapView.draw()` fills this rect last (on top of the bars)
with a low-alpha accent colour so it reads as a viewport window, not
another bar. Tests: with a fixture whose packed content is taller than
the view's own bounds (so the fallback `visiblePackedRect` — origin
zero, size equal to the editor's bounds, the same fallback the
production `visiblePackedRect()` already uses outside a real scroll
view — is a meaningful fraction of `packedHeight`), assert
`viewportRect(...)` is shorter than the minimap's own bounds height
(it's an indicator, not the whole track) and starts at the minimap's
top; then grow the editor's frame height and assert the computed
indicator height grows proportionally — a live geometric relationship,
not a flag (N9).

### T04: Fold-aware rendering; downsample at 5 MB scale

`MinimapRenderer.bars(from:)` (T01) already only sees
`snapshot.map.entries`, which `packedSourceLineEntries()` already
excludes hidden/folded lines from and packs contiguously — so
fold-awareness at the data level already exists; this task adds explicit
coverage for it at the render-plan level (not just the existing
snapshot-level fold test) plus downsampling. Add `MinimapRenderer.
defaultMaxBars` (a fixed constant, e.g. 512) and a `maxBars:` parameter
to `bars(from:maxBars:)`: when `entries.count <= maxBars`, keep today's
one-bar-per-line behaviour (small/medium docs keep full fidelity);
above that, bucket entries into exactly `maxBars` fixed-height slices of
`packedHeight` in a single forward pass (dominant kind per bucket:
heading beats fence beats body; coverage: the max coverage of any entry
in the bucket) — bounded output regardless of input size, computed once.
`MacMinimapView` caches the computed `bars` in `snapshot`'s `didSet`
(not inside `draw()`), so `draw()` itself only ever iterates the
bounded, cached array — no O(lines) work per repaint, only once per
document-change-driven snapshot update. Tests: (1) a synthetic
`MinimapSnapshot` built directly (not through a real 5 MB parse) with
5,000 synthetic `SourceLineMap.Entry` values asserts `bars(from:).count
<= defaultMaxBars` while `entries.count` is far larger, and a second
snapshot with fewer entries than `defaultMaxBars` asserts `bars.count ==
entries.count` (fidelity preserved below the threshold); (2) on the
existing fold fixture, assert bars computed from the folded snapshot
never extend past `folded.packedHeight` and that folding strictly
shrinks the total bar-covered span versus the unfolded snapshot's bars —
folded content does not render as if still expanded (N9).

### T05: Refresh on document change, not just on SwiftUI re-render

`FoldingTextView.onTextDidChange` already exists and is exactly the
change-notification mechanism the rest of the app uses —
`DocumentSession.init` subscribes it straight to `objectWillChange.send()`,
which is what drives SwiftUI (and therefore
`MacMinimapRepresentable.updateNSView`) to refresh. But today only
`insertTextAtCaret`/`replaceSelection` call it; `toggleFold(atSourceLine:)`,
`foldAll()`, `unfoldAll()`, `setMode(_:)`, and `setZoomScale(_:)` mutate
what should be drawn without ever calling it. This is the concrete gap
behind G.19's "refreshes only when SwiftUI happens to re-render":
`FoldingTextView.handleGutterClick(at:)` (a real chevron click) calls
`toggleFold(atSourceLine:)` directly — bypassing `DocumentHost`/
`DocumentSession` entirely — so today a real fold click never notifies
anything, and the minimap (and gutter chevrons drawn by other instances)
can go stale. Add `onTextDidChange?()` to the end of each of those five
methods on `FoldingTextView`, so the one existing notification path
fires reliably for every mutation that changes minimap-relevant state,
regardless of which call path reached it — hooking the existing
mechanism rather than adding a parallel one. Test: set
`view.onTextDidChange` to a counting closure and assert it increments
after each of `toggleFold(atSourceLine:)`, `foldAll()`, `unfoldAll()`,
`setMode(_:)`, and `setZoomScale(_:)` — a live counter that fails if any
call site is missing the hook (N9).
