# v1.2 Requirements

Product intent lives in `(2026-08-20) v1.2.md`. This file is the agreed architecture, the requirements, and the Tasks Breakdown that becomes tickets. Implementation plans are written **on each ticket**, not here.

Architecture: **C, unchanged spine.** SwiftUI chrome, Markus-owned TextKit 2, cmark-gfm, Swift block index, one app-scoped `ThemeStore`. v1.2 changes how Settings is presented, what a “theme” is (family + light/dark), and how Custom is authored. It does not replace the editor, parser, or document model.

## Overview

v1.2 is a **Settings and themes** release for **macOS**. It replaces the in-document settings takeover with a Preferences window (Warp-style category list, Editorio-style Appearance page), ships familiar light/dark theme families, and turns Custom into a clone-from-prebuilt editor with per-selector colors that Preview actually paints.

Shared `ThemeTokens`, store, and Preview substitution are cross-platform. Those changes must **build** on iOS and iPadOS. No new iPhone or iPad Settings UI.

Quality of this release is judged by **running the app**. Automated tests are not the gate.

## Goals

- A real Settings window that leaves the open document intact; gear, **Markus → Settings…**, and ⌘, all open it.
- Left category list, right detail (Appearance, Editor, About).
- Appearance page: Follow System, family cards with Light and Dark, rich proxy beside the grid, Custom on the same page.
- Replace Daylight / Lampblack / Fog / Parchment / Meadow / Harbor with Nord, Monokai, Solarized, GitHub, Catppuccin, Gruvbox — each Light and Dark.
- Copy any prebuilt variant into Custom; then edit H1–H6, emphasis, links, lists, code blocks, callouts, and the remaining painted roles.
- Minimal GitHub-style callouts in Preview so the callout color is visible.
- Hover previews the proxy only and does not stick. Committed theme stays app-scoped and persisted.

## Non-goals

- New iPhone or iPad Settings chrome.
- Language-aware highlighting inside fences.
- Theme file import/export, `.tmTheme` / VS Code themes, a marketplace.
- Per-window or per-document themes.
- CSS-like arbitrary selectors.
- Ribbon / library / document-window redesign except wiring the gear to the new window.
- Extra Editor settings beyond default open mode.
- Expanding the unit-test suite as a substitute for looking at the panel. No TDD requirement on this board.
- v1 skip list: side-by-side, PKM, AI, plugins, key remap, math, Mermaid, HTML preview, Windows/Linux, multi-cursor, project search, PDF/RTF export.

## Architecture

### Decisions (from the briefing’s open questions)

| Question | Decision |
|---|---|
| Family list | Nord, Monokai, Solarized, GitHub, Catppuccin, Gruvbox. No Markus-original family. Palettes are original sRGB recipes inspired by the public look, not copied from a vendor file. |
| Card grain | One card per **variant** (Nord Light, Nord Dark). Matches the reference picker. |
| Callouts | GitHub alerts: `> [!NOTE]`, `TIP`, `WARNING`, `IMPORTANT`, `CAUTION`. **One** callout color for chrome (background/border/label). Types differ by keyword and a SF Symbol, not five color wells. |
| Clone vs rebase | Custom is a **frozen snapshot**. Later catalog edits do not rewrite an existing Custom. |
| Source vs Preview | Granular colors apply in **Preview only**. Source stays 1:1 with the buffer (v1.1). |
| Editor category | Ships. Contents: default open mode (Preview / Source). |
| Window title | **Settings** (current macOS naming). |
| Custom density | Grouped disclosures: Headings, Emphasis, Blocks, Other — not twenty wells in one dump. |
| Follow System + Custom | Follow System applies to **named families** only. Custom is a single snapshot; the checkbox does not invent a second Custom variant. |
| Hover state | Hover lives in the Settings **view**, not as sticky `ThemeStore.hoverSelection` shared across windows. Closing Settings or applying a theme clears it. |

### Stack

| Layer | Choice | Change from v1.1 |
|---|---|---|
| Settings window | SwiftUI `Settings` scene (⌘, for free) containing a `NavigationSplitView` | **New** — replaces in-window `SettingsScene` swap |
| Appearance page | Cards + proxy column inside the Appearance detail | **Changed** |
| Theme identity | `family` + `variant` (light/dark), or `custom` | **Changed** — was six flat IDs |
| Follow System | App-scoped bool; maps family → variant from `effectiveAppearance` | **New** |
| Token model | Expanded `ThemeTokens` (per-heading, emphasis colors, callout) | **Changed** |
| Preview | Existing paragraph substitution, plus callout blocks and per-role colors | **Extended** |
| Theme store | Still one app-scoped `ThemeStore`; `themeChanged` still means committed only | Unchanged contract |
| Persistence | `UserDefaults` in the sandbox container | Extended keys |
| iOS Settings | Existing sheet; applies committed theme; no new picker | Unchanged chrome |

Minimum OS unchanged: macOS 14, iOS 17, iPadOS 17.

### Components

1. **Settings window.** The macOS `Settings` scene is the Preferences window. Inside it: a left list (`Appearance`, `Editor`, `About`) and a right detail. Not a sheet, not nested in the document `NavigationStack`, not a swap of `ContentView`. Minimum width must fit the Appearance inner split (cards | preview); if the window is narrowed, stack cards above preview. The sidebar does not collapse.

2. **Entry points.** Ribbon gear, **Markus → Settings…**, and ⌘, all open this same window (`showSettingsWindow:` / equivalent). Remove the stub `Settings { Text("Open a Markdown document to edit.") }`. Remove macOS `host.isSettingsPresented` document takeover.

3. **Appearance page.** Follow System at the top. Wrapping grid of variant cards plus Custom. Each card: short rendered snippet, chip strip, name, selection check. Click commits. Hover restyles only the proxy. Preview column: one `FoldingTextView` in Preview mode with a GFM sample covering H1–H3 at least, paragraph, bold/italic, link, inline code, fence, list, block quote, table, strikethrough, footnote, and a callout. Custom controls (grouped) when Custom is selected, including **Use as Custom** from the current or last-clicked prebuilt variant.

4. **Theme families.** Catalog type: `ThemeFamily` × `ThemeVariant`. Twelve prebuilt recipes, each a full `ThemeTokens`. Selecting a named card sets the family (and, if Follow is off, the pinned variant). Follow on: applied tokens are `catalog[family][systemVariant]`. Checkmark on the variant currently displayed. Clicking the family’s other variant while Follow is on keeps the family and Follow (system still chooses which you see). Clicking a different family selects that family.

5. **Theme store.** Still `ThemeStore.shared` for production. Isolated `UserDefaults` suites stay available for any leftover tests; this board does not require new ones. Persist: family, pinned variant, follow-system flag, selection case (named vs custom), every custom selector. `themeChanged` fires only on commit (selection, follow toggle, custom edit) — never on hover.

6. **Token model and Preview.** Replace the single `heading` color with H1…H6. Add `bold`, `italic`, `boldItalic` colors used by inline substitution (traits remain). Keep background, body, link, list, fence, inline code, table, strikethrough, footnote, fold marker. Add `callout`. Preview substitution reads the new fields. Source mode ignores them.

7. **Callouts.** Parse GitHub alert blockquotes in the Preview path. Render a distinct block (label + body) using `tokens.callout` for chrome and body/emphasis tokens for inner text. Unknown `> [!FOO]` degrades to a normal block quote. Not a fold type in this release.

8. **Clone to Custom.** “Use as Custom” copies the chosen variant’s full token set into the custom store, selects Custom, leaves the catalog untouched. If Custom already differs from a fresh clone, confirm replace before overwriting.

9. **Editor page.** Default mode for newly opened and untitled documents: Preview (default) or Source. Persisted. Changing it does not restyle already-open windows.

10. **About page.** App name and short version from the bundle.

### Data model

```text
ThemeFamily     nord | monokai | solarized | github | catppuccin | gruvbox
ThemeVariant    light | dark
ThemeSelection  named(family) | custom

ThemeStore      // app-scoped
  followSystem: Bool
  selection: ThemeSelection
  pinnedVariant: ThemeVariant      // used when followSystem is false
  custom: ThemeTokens              // snapshot; all selectors persisted

ThemeTokens
  background, body
  h1, h2, h3, h4, h5, h6
  bold, italic, boldItalic
  link, list
  inlineCode, fence
  table, strikethrough, footnote, foldMarker
  callout

Applied theme
  if selection == custom → custom tokens
  else if followSystem → catalog[family][systemIsDark ? dark : light]
  else → catalog[family][pinnedVariant]
```

Disk files remain Markdown only. Theme state never writes into `.md`.

### Key flows

**Open Settings.** Gear / menu / ⌘, brings the Settings window forward. Document windows stay as they are.

**Pick a family.** Click Nord Dark → selection becomes named(nord). If Follow is on, applied tokens follow the system; if off, pinnedVariant becomes dark. `themeChanged` updates every open document immediately. Persist.

**Follow System.** Toggle on: named selection uses the system variant; Custom unchanged. Toggle off: pin the variant currently showing.

**Hover.** Pointer over a card restyles the proxy from that card’s tokens. Leave / close / click-apply clears hover. Open documents stay on committed tokens.

**Use as Custom.** Snapshot variant tokens into `custom`, select custom, persist, apply, confirm if replacing existing custom edits.

**Edit Custom.** Color well (or grouped control) writes one selector, persists, `themeChanged`. Preview (documents + proxy) shows it.

**Open a file / untitled.** Use Editor default mode. Theme is whatever is already committed in the store.

## Requirements

- **R1.** macOS Settings is a separate window with a left category list (Appearance, Editor, About) and a right detail pane. It does not replace the document viewport.
- **R2.** The ribbon gear, **Markus → Settings…**, and ⌘, open that window. The v1.1 stub Settings scene and in-window takeover are gone.
- **R3.** Appearance shows Follow System Appearance, one card per catalog variant plus Custom, and a proxy column with the rich GFM sample. Click applies globally; hover previews the proxy only.
- **R4.** Shipping catalog is Nord, Monokai, Solarized, GitHub, Catppuccin, Gruvbox, each Light and Dark. The six v1.1 names are not in the picker.
- **R5.** Follow System maps the selected **family** to Light or Dark from system appearance, in every open window. It does not apply to Custom.
- **R6.** Theme choice, follow flag, pinned variant, and Custom tokens persist across relaunch (sandbox `UserDefaults`).
- **R7.** Any prebuilt variant can be copied into Custom. Named recipes stay immutable. Custom is a frozen snapshot.
- **R8.** Custom exposes grouped color controls for: background, body, H1–H6, bold, italic, bold-italic, links, lists, fenced code, inline code, callouts, tables, strikethrough, footnotes, fold markers. Those colors are visible in Preview.
- **R9.** Preview renders GitHub-style alerts and uses the callout token for their chrome.
- **R10.** Editor page: default open mode Preview or Source, persisted, used for new and newly opened documents.
- **R11.** About page: app name and version.
- **R12.** Closing Settings does not tear down or rebuild the document editor. Hover does not stick after close or across a second Settings window.
- **R13.** iOS/iPadOS still **build**. Their Settings sheet need not gain the new picker.

### Non-functional

- **N1.** Palettes are original sRGB values. Contrast of body, links, and fold markers on the background must be readable when you sit in front of the window — not “we’ll polish later.”
- **N2.** `themeChanged` never fires on hover.
- **N3.** Shared-layer edits must compile for macOS, iOS, and iPadOS.
- **N4.** No new unit-test suite work is required to close a ticket. Do not add tests that cannot fail, and do not block on `xcodebuild test`.

## Acceptance criteria

- [ ] Gear, Settings menu, and ⌘, open one Settings window; the Markdown document remains on screen.
- [ ] Appearance, Editor, and About are selectable in the left list.
- [ ] Twelve named variant cards plus Custom; old six names gone.
- [ ] Follow System switches Light/Dark with macOS appearance for a named family; Custom is unaffected.
- [ ] Hover restyles only the proxy; click restyles every open document; relaunch restores the choice.
- [ ] Use as Custom, then change H1 without changing H2; Preview shows that.
- [ ] A `> [!NOTE]` block is visibly a callout, not a plain quote.
- [ ] New document follows the Editor default mode.
- [ ] macOS Debug **build** succeeds after each task; iOS/iPadOS **build** succeeds when shared code changed.

## Testing requirements

This board **verifies by building**, not by running MarkusTests. Theme and Settings bugs show up in the window; the existing suite has not caught them.

After **every** plan task, from `Markus/`:

```text
xcodebuild -project Markus.xcodeproj -scheme Markus -destination 'platform=macOS' -configuration Debug build
```

If the task touched `ThemeTokens`, `ThemeStore`, Preview substitution, the parser, or any file compiled into the iOS target, also:

```text
xcodebuild -project Markus.xcodeproj -scheme Markus -destination 'platform=iOS Simulator,name=iPhone 17' -configuration Debug build
xcodebuild -project Markus.xcodeproj -scheme Markus -destination 'platform=iOS Simulator,name=iPad Pro 13-inch (M5)' -configuration Debug build
```

Ticket **Verify:** lines copy these build commands. Do not invent `xcodebuild test` or TDD RED/GREEN as the bar.

After a UI task, the implementer (or human) **runs the app** and looks at the Settings window. That inspection is part of done, not an automated test.

## Commit criteria

Before marking a ticket or subtask done, and before any git commit:

- [ ] The task’s `xcodebuild` **build** command(s) succeeded
- [ ] The change meets the matching requirement and acceptance criteria
- [ ] For Settings/theme UI: the panel was launched and checked by eye
- Commit message format: `{ticket-id} {task-id}: {title}`

Do not require the unit-test suite to pass as a ticket gate. Do not write a failing test first.

## Tasks Breakdown

Each item becomes one ticket after this file is approved. The implementation plan is written on the ticket (`bora-plan`), not here.

1. **Settings window and navigation** — SwiftUI `Settings` scene with sidebar (Appearance, Editor, About placeholders). Wire gear, app Settings menu, and ⌘,. Kill the stub Settings text. (R1, R2)
2. **Retire in-document settings takeover** — remove macOS `ContentView` swap to `SettingsScene`; document editor stays mounted while Settings is open. (R1, R12)

6. **Expanded tokens in Preview** — H1–H6, bold / italic / bold-italic colors, keep existing roles; Source unchanged. (R8)
7. **Callouts** — parse GitHub alerts; render with `tokens.callout`. (R9)
8. **Use as Custom and granular controls** — clone snapshot, confirm replace, grouped color wells bound to the expanded tokens. (R7, R8)
9. **Editor default mode and About** — persisted Preview/Source default; About shows name and version. (R10, R11)

Do not create tickets for non-goals.

## Risks and assumptions

- **Callout parsing is new Preview surface.** If GitHub-alert detection fights nested block quotes, stop and reopen design rather than silently painting every quote as a callout.
- **Twelve full palettes in one ticket** will look wrong until someone looks at them in the window. That is expected; N1 is a human pass, not a contrast-ratio CI job.
- **SwiftUI `Settings` + `NavigationSplitView`** may fight window sizing. If the system Settings scene cannot host the Editorio inner split, fall back to an app-owned `NSWindow` that ⌘, still opens — same IA, different host. That fallback does not need a new Requirements file if the user-visible layout is unchanged.
- **Custom persistence size** grows with the token set. Still `UserDefaults`; if a single plist becomes awkward, stay with defaults unless it actually fails.
- **iOS sheet** will show old chrome while applying new tokens. Acceptable for this release (R13).

## Open questions

None blocking. Overrides from the human (different family, per-type callout colors, Settings vs Preferences title) can land as edits here before tickets.
