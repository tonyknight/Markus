# Markus v1.2 — Planning

v1.1 made Markus evaluable as a Mac Markdown app: real menus, rendered Preview, Source editing, a ribbon, and a theme picker that actually selects. It did **not** make Settings a place anyone would choose to spend time. The panel replaces the document, the six named palettes are unfamiliar and unappealing, Custom exposes four coarse colors, and **Markus → Settings… / ⌘,** still opens a stub.

v1.2 is a **Settings and themes** release. It replaces the in-window settings takeover with a real Preferences window, rebuilds the prebuilt catalog as light/dark families people already know, and turns Custom into a clone-and-refine editor with selectors that match how Markdown is actually styled.

This briefing is the basis for `(2026-08-20) v1.2 Requirements.md`. Architecture is **not** agreed until that conversation happens. Do not treat the catalog names or selector list below as frozen Requirements.

## Background

Markus is a free, open-source, native Markdown app for macOS, iOS, and iPadOS. Files on disk stay plain UTF-8. Theme, folds, zoom, and recents live in app storage. MIT licensed.

v1 / v1.1 architecture **C** stays: SwiftUI chrome, Markus-owned TextKit 2, cmark-gfm, Swift block index. One app-scoped `ThemeStore` already broadcasts a committed theme to every open window and tab. Hover preview already paints a proxy, not the real document. Those two behaviours are load-bearing and must survive this release.

What v1.1 shipped for Settings is the problem:

1. **The surface is the wrong kind of window.** The gear swaps the entire document viewport for `SettingsScene`. Closing Settings tears down and rebuilds the editor view. The user cannot see their own file while choosing a theme. ⌘, and the app Settings menu are a placeholder: “Open a Markdown document to edit.”
2. **The left/right chrome is empty.** There is one category (Themes). The sidebar does not earn its width. The theme grid and a two-line proxy are stacked in the leftover space, so neither is readable.
3. **The six palettes are not a product.** Daylight, Lampblack, Fog, Parchment, Meadow, and Harbor are distinct sRGB recipes, but they are not themes users recognize, they are not light/dark pairs, and they ignore system appearance. Lampblack is a manual dark canvas; the rest are light or mid-grey.
4. **Custom is a dead end.** Background, Auto/Light/Dark text, and optional heading / body / link / fence. There is no way to start from a named theme. One heading color covers H1–H6. Bold, italic, and bold-italic share the parent color and only change font traits. Callouts are not a token and are not rendered.
5. **The proxy does not exercise the palette.** Sample Markdown is a heading, a sentence, a link, and inline code. Fence, list, table, strikethrough, footnote, and fold-marker colors exist in every named theme and never appear in the picker.

Reference layouts agreed in conversation (not to clone as products):

- **Warp Settings** — dedicated window, left category list, right detail.
- **Editorio Appearance** — Follow System, theme cards, a first-class preview column, custom controls on the same page.

v1.2 combines those: Warp’s **window and navigation**, Editorio’s **Appearance page**.

## What's in, at a glance

| Area | v1.1 | v1.2 |
|---|---|---|
| Surface | Full-viewport swap inside the document | Separate Preferences window |
| Navigation | One “Themes” row | Category list (Appearance, Editor, About) |
| Entry | Ribbon gear only | Gear **and** Markus → Settings… / ⌘, |
| Prebuilt | Six unrelated Markus names | Familiar families, each with Light and Dark |
| System appearance | Ignored | Follow System uses the family’s matching variant |
| Custom | Four optional colors | Clone any base theme, then edit a full selector set |
| Proxy | Two lines under the grid | Rich GFM sample beside the cards |
| Hover | Shared `hoverSelection` on the store | Preview stays proxy-only; hover must not stick across windows or after close |

## Goals

- Replace the document-takeover settings surface with a **Preferences window** that leaves the open document intact.
- Give that window a **left category list and a right detail pane** (Warp). Appearance is the first page and the one this release designs in full.
- Make the Appearance page a **theme-card grid plus a real preview column** (Editorio), not a stacked two-line proxy.
- Replace the six Markus palettes with **light and dark variants of themes people already know** (Nord, Monokai, and a short additional set — catalog confirmed in Requirements).
- **Follow System Appearance**: Light Mode uses the family’s light variant, Dark Mode the dark variant. Turning it off pins one variant.
- Let the user **copy any prebuilt (family + variant) into Custom** and then modify it. Named presets stay immutable.
- Give Custom **per-selector colors** that match Markdown structure: H1–H6, body, bold, italic, bold-italic, links, lists, fenced code blocks, callouts — plus the token roles we already paint (inline code, tables, strikethrough, footnotes, fold markers, background).
- Keep committed theme changes **app-scoped** and persisted. Hover still must not restyle open documents.
- Close the v1.1 Settings defects listed under **Issues this release absorbs** below.

## Non-goals

- New iPhone or iPad Settings chrome. Shared `ThemeTokens` / store changes must keep those destinations building and green; the iOS sheet may keep applying the committed theme without the new picker.
- Language-aware syntax highlighting inside fences (v1.1 non-goal, still true — the proxy shows fenced text styled as a code *block*, not a language grammar).
- User-authored theme files, import/export of `.tmTheme` / VS Code themes, or a theme marketplace.
- Per-window or per-document themes. Theme remains app-scoped.
- Side-by-side Source and Preview, PKM, AI, plugins, key remapping, math, Mermaid, Windows/Linux.
- A general-purpose CSS-like selector language. Custom is a fixed list of Markdown roles, not arbitrary queries.
- Redesigning the ribbon, library, or document window chrome except where the gear must open the new Preferences window.
- Filling Editor/About with speculative settings. Editor may hold **default open mode** (Preview / Source) if Requirements keeps it; nothing else is in this release unless the design conversation adds it by name.

## Target users

The same people as v1: they keep Markdown as files and want a native app. v1.2 is for the person who opens Settings expecting a Mac Preferences window and a theme they have seen in a terminal, editor, or GitHub — and who then wants to tweak headings and emphasis without starting from a blank custom palette.

## User stories

- As a Mac user, I press ⌘, or choose **Markus → Settings…** and get the same Preferences window the ribbon gear opens, without losing my document.
- As a Mac user, I see a short list of settings categories on the left and the active category on the right.
- As a reader, I pick **Nord** (or another familiar family) and see a light and a dark card I recognize, previewed in a document that actually contains headings, a quote, a fence, a list, a link, and a table.
- As a reader, I enable **Follow System Appearance** and Markus tracks Light/Dark Mode using that family’s matching variant, in every open window.
- As a reader, I click **Use as Custom** on a prebuilt variant, then change H1 independently of H2, and bold independently of body text.
- As a reader, hovering a card restyles only the Preferences preview; my open files do not flicker. Closing Preferences clears any hover.
- As a writer, I can set a default of Preview or Source for newly opened files (if Editor ships in this release).

## What v1.2 addresses

### A. Preferences window and navigation

Today Settings is `ContentView` swapping to `SettingsScene`. That violates Mac convention and is the root of the teardown/focus bugs.

v1.2 presents a **separate window**:

- Title: Settings (or Preferences — decide in Requirements; macOS Sequoia uses Settings).
- Left: category list. Proposed first cut: **Appearance**, **Editor**, **About**. No search, no account, no “open settings file”.
- Right: the selected category’s page.
- Minimum width enough for Appearance’s inner split (cards | preview), with the inner split stacking vertically if the window is narrowed. The sidebar does not collapse.
- Ribbon gear, ⌘,, and the app Settings menu all open **this** window. The SwiftUI `Settings { Text("Open a Markdown document…") }` stub goes away.
- Closing the window does not replace or rebuild the document editor.

iOS stays on the existing sheet for this release.

### B. Appearance page (theme picker)

The right pane for Appearance is **not** a vertical form. It is the Editorio-style page:

1. **Follow System Appearance** at the top, with one sentence of explanation.
2. **Theme cards** in a wrapping grid: one card per family variant (Light / Dark), plus Custom. Cards show a short rendered snippet, a chip strip, a name, and a selection check. Click applies. Hover (Mac) previews in the proxy only.
3. **Preview column** beside the grid: a single proxy `FoldingTextView` in Preview mode, using a GFM sample that includes heading levels, paragraph, link, inline code, fenced block, list, block quote, table, strikethrough, and — if callouts ship — a callout. This is the only place hover restyles.
4. **Custom** controls below (or shown when Custom is selected): clone source, then per-selector color (and where we already have it, text style Auto/Light/Dark for the roles that still derive from background luminance).

Committed apply remains global (`ThemeStore.themeChanged` → every `DocumentHost`). Hover must not live as sticky shared store state that another window or a later reopen can still see.

### C. Prebuilt catalog (families, not six one-off recipes)

Drop Daylight, Lampblack, Fog, Parchment, Meadow, and Harbor as the shipped set. Replace them with **families**. Each family has a Light and a Dark variant. Follow System picks between those two.

Proposed starting catalog (names to confirm; palettes must be original implementations inspired by the public look of these themes, not copied from a vendor’s licensed file):

| Family | Why it’s here |
|---|---|
| **Nord** | Explicitly requested; widely recognized polar palette |
| **Monokai** | Explicitly requested; classic editor dark, with a light companion |
| **Solarized** | Canonical light/dark pair; already the shape of the reference UI |
| **GitHub** | Matches how a large share of Markdown is read |
| **Catppuccin** | Current, familiar Latte / Mocha pairing |
| **Gruvbox** | Strong light/dark pair people know from terminals |

Six families × two variants is twelve prebuilt cards — comparable to the reference grid, not an unbounded store.

Each variant is a **full token recipe** (every selector in §D), not a single heading/body pair. Contrast on background vs body, links, and fold markers is part of “done”, not a later polish ticket.

### D. Custom: clone, then granular selectors

**Clone.** Any prebuilt variant can be copied into Custom in one action (“Use as Custom” / equivalent). That snapshots every selector into the custom store, selects Custom, and leaves the named family unchanged. If Custom already has edits, the copy confirms replace (Requirements can specify the exact prompt).

**Selectors.** Custom must expose at least:

- Background
- Body (normal paragraph text)
- Headings **H1, H2, H3, H4, H5, H6** as six independent colors
- **Bold**, **italic**, **bold-italic**
- **Links**
- **Lists** (markers / list text — one control unless design splits them)
- **Code blocks** (fenced)
- **Callouts**
- Existing roles we already paint and should not orphan: inline code, tables, strikethrough, footnotes, fold markers

Today `ThemeTokens` has one `heading` color; Preview already *sizes* H1–H6 via `PreviewHeadingScale` but tints them all with `tokens.heading`. Bold/italic are font traits on the parent color. v1.2 has to **widen the token model and the substitution path**, not only add color pickers that write unused keys.

**Callouts.** Preview has no callout element today. A Custom slider for callouts is dishonest unless Preview paints them. v1.2 should include a **minimal GitHub-style alert** (`> [!NOTE]`, and the usual tip/warning/important/caution set) so the token is visible in the document and the proxy. Exact syntax and how many types share one color vs four colors is a Requirements decision.

### E. Issues this release absorbs

These were identified against the v1.1 Settings/theme implementation and are in scope, not a later cleanup list:

1. **⌘, / Settings menu stub** — must open the real Preferences window.
2. **Named themes ignore system appearance** — Follow System + paired variants.
3. **Proxy sample too thin** — GFM-complete proxy beside the cards.
4. **Settings unloads the document** — separate window; no viewport swap.
5. **Hover stuck on the shared store** — hover is preview-only and cleared when the pointer leaves, the window closes, or a theme is applied. Two Preferences windows must not share a sticky hover.
6. **Sidebar with one category** — real category list; Appearance is not alone even if Editor and About are thin.
7. **Quality leftovers** — remove dead flags such as `hostsPickerInSettings`; do not ship palettes with unreadable fold markers or links. No unused “Settings” SwiftUI scene left behind.

## Constraints

- Spine stays architecture C. Do not replace TextKit 2 or cmark-gfm for theming.
- `ThemeStore` stays app-scoped. Tests that construct an isolated `ThemeStore(defaults:)` must keep working.
- Persistence stays `UserDefaults` (sandbox container). Custom’s larger token set must round-trip a relaunch.
- Named palettes are sRGB recipes in code (same pattern as `NamedThemeCatalog`), not runtime downloads.
- Shared editor/parser changes must not regress iOS/iPadOS **builds or tests**, even though new Settings UI is macOS-first.
- Hover must not trigger `themeChanged` (that would reparse every open document — the v1.1 bug the proxy was built to avoid).
- Cloning a theme must not mutate the catalog; custom is a separate persisted snapshot.

## Success criteria

- A Mac user can open Settings from the gear, the Settings menu, and ⌘,; all three show the same window; the document they were reading is still there.
- Appearance shows familiar light/dark families, Follow System works, and the preview is a real Markus Preview of a rich sample.
- Choosing a theme still updates every open window immediately and survives relaunch.
- Custom can be filled from any prebuilt variant and then override H1–H6, emphasis, links, lists, code blocks, and callouts, with those overrides visible in Preview (and in the proxy).
- The six v1.1 Markus names are gone from the shipping picker.
- iOS/iPadOS still build and the existing test destinations stay green.

## Open questions for Requirements

These are briefing-level; they need answers before tickets exist.

1. **Final family list.** Keep the six proposed families, drop one, add one (e.g. Tokyo Night)? Any Markus-original family, or only familiar names?
2. **Card grain.** One card per variant (Nord Light, Nord Dark) vs one card per family that switches with Follow System / a Light-Dark toggle. The reference UI used one card per variant.
3. **Callout syntax and granularity.** One callout color, or per-type (note/tip/warning/important/caution)? GitHub alerts only, or also Obsidian `> [!note]` folding callouts?
4. **Clone vs dual-write.** If the user clones Nord Dark, then Nord Dark is updated in a later Markus release, does Custom stay frozen (yes — recommended) or re-base?
5. **Source mode.** Do granular colors apply in Source (syntax-tinted source) or only in Preview? v1.1 Preview is the styled reading surface; Source is largely monochrome 1:1 with the buffer.
6. **Editor category.** Ship default open mode in v1.2, or Appearance only plus a stub Editor/About?
7. **Window title.** Settings vs Preferences.
8. **Custom control density.** All selectors on one scrolling page, or grouped disclosure (Headings, Emphasis, Blocks)?
